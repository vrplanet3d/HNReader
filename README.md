# HNReader

An ASP.NET Core API using .NET 8 that returns Hacker News best stories ranked by **score**.
The standard .NET 8 project and `HNReader.sln` open in Visual Studio 2022 (17.8+) on Windows.
The same source also builds on macOS and Linux.

## Requirements and run instructions

- .NET 8 SDK (on macOS, Windows, or Linux). This provides the `dotnet` command.
- On Windows, Visual Studio 2022 17.8+ with the ASP.NET and web development workload is optional.

From the repository root, run `dotnet build HNReader.sln`. To use HTTPS locally,
run `dotnet dev-certs https --trust` if the .NET development certificate is not
yet trusted (your OS may ask for confirmation). Then run
`dotnet run --project src/HNReader.Api --launch-profile https` and request
`https://localhost:7169/api/stories/best?n=10` in a browser or HTTP client.
The `https` profile also listens on `http://localhost:5261`.

For a quick local HTTP-only run without trusting a development certificate, use
`dotnet run --project src/HNReader.Api --launch-profile http` and request
`http://localhost:5261/api/stories/best?n=10`. Development requests to the
HTTP port are not automatically redirected to HTTPS. For public deployment,
serve the API over HTTPS and decide which component manages the certificate
and redirects HTTP requests to HTTPS.
Alternatively, open `HNReader.sln` in Visual Studio, select `HNReader.Api` as the
startup project, and run it (the Visual Studio HTTPS or IIS Express profile may
use a different port). `src/HNReader.Api/HNReader.Api.http` contains a sample request.

### Local ports and changing them

- The local addresses are set in the `http` and `https` profiles in
  `src/HNReader.Api/Properties/launchSettings.json`. The HTTP profile uses port
  5261. The HTTPS profile uses port 7169 for HTTPS and also binds HTTP on 5261.
  IIS Express has separate ports in the same file.
- These are randomly selected development ports generated by the ASP.NET Core
  project template. They are not required ports or the standard HTTP and HTTPS
  ports (80 and 443). You can choose other available local ports.
- To change the port for one run, keep the development profile and use this command:
  `dotnet run --project src/HNReader.Api --launch-profile https -- --urls https://localhost:7443`.
  The app now listens only on HTTPS port 7443. Change the port in the URL you
  request and in `src/HNReader.Api/HNReader.Api.http` if using its sample requests.
- To change the default port for this project, edit `applicationUrl` in the
  selected profile in `launchSettings.json`. If you commit this change, it also
  changes the default for other developers.
- `ASPNETCORE_URLS` is another option for scripts and environment-specific
  settings. Run without a launch profile so its `applicationUrl` does not
  override the environment variable. On macOS or Linux, for example, run
  `ASPNETCORE_ENVIRONMENT=Development ASPNETCORE_URLS=https://localhost:7443 dotnet run --project src/HNReader.Api --no-launch-profile`.
  On Windows PowerShell, set these two environment variables in the shell
  before running the same `dotnet run` command. Trust the development HTTPS
  certificate for any local HTTPS address.

Run the tests with `dotnet run --project tests/HNReader.Tests`. They do not
need internet access or extra test packages. This project uses a small console
test runner, so `dotnet test` does **not** run these tests.

## Using the API

`GET /api/stories/best?n=<positive integer>` returns a JSON list with the fields
`title`, `uri`, `postedBy`, `time`, `score`, and `commentCount`. The highest score
comes first. When scores tie, the story with the smaller Hacker News ID comes
first. The `time` field is a UTC date and time in ISO 8601 format. Missing story
URLs and authors are returned as `null`. Missing comment counts become `0`.
Add `pretty=true` to make the JSON easier to read, for example
`/api/stories/best?n=10&pretty=true`. Omit `pretty` or use `pretty=false` for
compact JSON. Both formats contain the same stories in the same order.
If `n` is missing, not a number, zero, or negative, the API returns HTTP 400.
If `n` is larger than the number of available stories, it returns all of them.
If Hacker News is unavailable and the API has no saved results to use, it
returns HTTP 503.
Values of `pretty` other than `true` or `false` return HTTP 400.

## How stories are chosen and cached

- "Best stories" means only stories listed by Hacker News at
  `/v0/beststories.json`, not every story on the site. The API gets the details
  for every listed ID, sorts the stories by score, and then returns the top `n`.
- The API skips missing or deleted items, items marked dead, other item types,
  and stories missing a title, score, or time. If a request to Hacker News fails
  or returns malformed JSON or a time outside the supported date range, the
  update fails instead of risking a wrong ranking.
- The app saves the sorted list and reuses it for any value of `n`.
  - Saved results are used for five minutes before another update is needed.
    Updating once a minute would make hundreds of requests to Hacker News
    from each running copy of the app, so five minutes reduces that load.
  - Only one update runs at a time in each copy of the app. It fetches up to
    8 stories at once, allows 10 seconds for each HTTP request, and allows up
    to 30 seconds for the whole update. Other callers can use the last saved
    list while the update is running, as long as that list is not too old.
  - If an update fails, the app waits one minute before trying again. It can
    keep returning the previous list for 15 more minutes after the initial
    five minutes. After that it returns HTTP 503 until Hacker News is available
    again. The results are not guaranteed to be current at every moment.
- Hacker News does not publish a rate limit for its API. Saving results and
  running only one update at a time stops a surge of requests to this API from
  causing a matching surge of requests to Hacker News. Each running copy of
  this app has its own saved list, which is not shared with other servers.

## Roadmap

These items are ordered for a public deployment with one running copy of the app.
The last two apply only if the deployment needs them.

1. Add tests that call the API over HTTP.
   - Check successful responses, invalid input, errors when Hacker News is
     unavailable, and the compact and readable JSON formats.
2. Set up HTTPS before exposing the app publicly.
   - Decide whether the app or a reverse proxy or load balancer handles HTTPS
     and its certificate. The component handling this is said to terminate TLS.
   - Decide where to redirect HTTP requests to HTTPS. The app currently does
     this outside Development. If a proxy handles HTTPS, configure trusted
     forwarded headers so the app knows the original request used HTTPS.
     Otherwise redirects can repeat indefinitely. The exact setup depends on
     where the app is hosted.
3. Limit how often each client can call the public API.
   - Return HTTP 429 when a client exceeds the limit. Saved results protect
     Hacker News but do not limit traffic coming into this app.
4. Add monitoring, error reporting, and health checks.
   - Track failed Hacker News requests and how old the saved results are. Alert
     if updates keep failing or the saved list becomes too old.
   - Report unexpected app errors to a tool such as Sentry, so they can be
     investigated. Error reporting alone would not show a stopped update job.
   - Add a health check endpoint so the hosting platform can tell whether the
     app is responding. If a scheduled job is added, monitor that it still runs.
5. Make the app easier to tune for higher traffic.
   - Allow timeouts and cache times to be changed without editing code. Test
     how the app behaves with many callers at once.
6. Add OpenAPI documentation describing the API and its responses.
7. If running more than one copy of the app, use one scheduled update job and
   a shared cache such as Redis.
   - The job would fetch and sort stories every five minutes, then replace the
     whole saved list in the shared cache at once. All API copies would read
     that list instead of fetching from Hacker News themselves.
   - This makes one set of Hacker News requests for the whole deployment and
     keeps client requests fast even while the list is updating. It also avoids
     having API copies compete to decide which one should update the list.
   - Keep the last good list when an update fails, monitor whether the job is
     running, and ensure only one job updates the list at a time. This approach
     does make scheduled updates even when there are no clients.
8. If private access or limits per client are needed, add API keys or sign-in.
